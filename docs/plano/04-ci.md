# Fase 4: repositórios no GitHub, CI e publicação das imagens

**Entrega:**
- Uma organização no GitHub (`<org>`) com os 3 repositórios públicos: `shortener-api`, `shortener-web` e `shortener-deploy`.
- O plano (`docs/plano/`) e as specs (`docs/superpowers/`) passam a viver no `shortener-deploy`.
- Todo PR no `shortener-api` e no `shortener-web` roda lint, typecheck, testes e o build da imagem ARM64.
- Todo merge na `main` publica `ghcr.io/<org>/shortener-api:sha-<7>` ou `ghcr.io/<org>/shortener-web:sha-<7>`.
- A `main` da api e do web só aceita mudanças por PR com CI verde.

**Custo:** zero. O plano Free de organização cobre repositórios públicos, GitHub Actions (inclusive runners ARM) e GHCR público.

Em todo o plano, `<org>` é o nome da organização no GitHub (neste projeto, `shortener-lab`), **em minúsculas**. O GHCR não aceita letras maiúsculas.

**Pré-requisitos:** Fase 2 concluída (a api com OIDC, na pasta do `shortener-api`) e Fase 3 concluída (o painel em `~/Documents/projects/shortener-web`).

## Por que 3 repositórios

Até aqui, tudo morava numa pasta só. A partir desta fase, o projeto fica dividido como em empresa:

| Repo | O que tem | O que publica |
|---|---|---|
| `shortener-api` | Código da api, do worker e do setup, migrations, testes, `Dockerfile`, compose de dev | Imagem `shortener-api:sha-<7>` |
| `shortener-web` | Painel React, testes, `nginx/`, `Dockerfile` | Imagem `shortener-web:sha-<7>` |
| `shortener-deploy` | Kustomize (`apps/`), Terraform (`infra/`), `scripts/`, `load/` e o plano | O estado desejado de cada ambiente |

**Por que separar a configuração do código?** É o padrão recomendado pela documentação do ArgoCD ("keep config in a separate Git repository"):
- **Histórico limpo.** Um commit no `shortener-deploy` é sempre "o que mudou em qual ambiente". No repo de código, o histórico fica só com mudanças de código.
- **Sem loop de CI.** O pipeline que publica a imagem faz commit da nova tag em outro repo. Se fosse no mesmo repo, esse commit dispararia o CI de novo.
- **Permissões diferentes.** Quem pode mexer em produção (o repo de deploy) não precisa ser quem pode mexer no código, e vice-versa. Na Fase 8, um GitHub App só terá escrita no `shortener-deploy`.
- **Ciclos de release independentes.** A api e o painel são versionados, testados e promovidos separadamente. Produção pode rodar a api `sha-aaa` com o web `sha-bbb`; o contrato entre eles é a API REST, que precisa continuar compatível com a versão anterior.

Os 3 ficam como pastas irmãs no seu Mac:

```
~/Documents/projects/
├── shortener-api/      # criado na Fase 1
├── teste/              # só guarda o plano até a Tarefa 4.3 (depois pode ser arquivada)
├── shortener-web/      # criado na Fase 3
└── shortener-deploy/   # criado nesta fase
```

Os 3 repos são públicos: o ArgoCD e o cluster leem o Git e as imagens sem credencial. Segredos nunca entram no Git, então isso é seguro.

### Por que uma organização, e não o seu usuário

Em empresa, os repositórios não moram na conta de ninguém. A organização é a "empresa"; o seu usuário é o crachá de quem trabalha nela. Se a pessoa sai, o código, as imagens e as automações ficam.

| Assunto | No usuário pessoal | Na organização |
|---|---|---|
| Dono do código | Você | A org; você é *owner* dela |
| Imagens | `ghcr.io/<seu-usuario>/shortener-api` | `ghcr.io/<org>/shortener-api` |
| GitHub App da Fase 8 | Registrado no seu perfil | Registrado na org, instalado só nos repos dela |
| Variáveis e segredos | Repetidos em cada repo | Uma vez na org, liberados para os repos escolhidos |
| Times e CODEOWNERS | Não existem | `@<org>/<time>` como dono de pastas ou repos |

A organização **não** junta os repos: continuam sendo 3, pelos motivos da seção anterior. Ela só dá um dono comum a eles.

## Rotina de PR (use daqui em diante, nos 3 repos)

```bash
git switch -c <tipo>/<assunto>          # ex.: ci/workflow, feat/me-links, infra/organization
# ... edite, rode os testes localmente ...
git add <arquivos> && git commit -m "<tipo>: <o que mudou>"
git push -u origin HEAD
```

## Tarefa 4.4: CI do `shortener-api`

**Arquivos:** criar `.github/workflows/ci.yml` no `shortener-api`.

**Conceitos:**
- *Service containers* dão um Postgres e um Valkey reais no CI, iguais aos do compose.
- O cache de dependências do npm acelera as execuções.
- Com `concurrency`, um push novo cancela o CI antigo do mesmo PR.
- Um workflow reutilizável (`workflow_call`) pode ser chamado por outro; o Release vai chamá-lo.
- O CI roda em **todo** PR, sem filtro de `paths`. Se um PR só de documentação pulasse o CI, os checks obrigatórios da Tarefa 4.7 nunca apareceriam e o PR ficaria travado.
- **O serviço `oidc` (mock-oauth2-server) não entra no CI.** Ele existe no compose para o painel em dev. Os testes da Fase 2 geram as próprias chaves RSA e assinam os tokens localmente, então o verificador de JWT nunca precisa buscar um JWKS de verdade.

- [x] **Passo 1: crie** `.github/workflows/ci.yml`

```yaml
name: CI

on:
  pull_request:
  workflow_call:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  app:
    runs-on: ubuntu-24.04
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_USER: shortener
          POSTGRES_PASSWORD: shortener
          POSTGRES_DB: shortener_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U shortener"
          --health-interval 5s --health-timeout 5s --health-retries 20
      valkey:
        image: valkey/valkey:8
        ports: ["6379:6379"]
        options: >-
          --health-cmd "valkey-cli ping"
          --health-interval 5s --health-timeout 5s --health-retries 20
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test:unit
      - run: npm run test:integration

  docker:
    runs-on: ubuntu-24.04-arm   # build nativo ARM64, igual aos nós t4g do EKS
    steps:
      - uses: actions/checkout@v7
      - uses: docker/setup-buildx-action@v4
      - uses: docker/build-push-action@v7
        with:
          context: .
          push: false
          platforms: linux/arm64
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

Os testes de integração usam os padrões de `test/integration/helpers.ts` (`localhost:5432/shortener_test` e `localhost:6379/1`), que batem com os service containers. Por isso o job não precisa de `env:`.

As versões das *actions* acima eram as majors atuais em outubro de 2026. A fonte da verdade é a página de releases de cada uma (`github.com/actions/checkout/releases`, `github.com/docker/build-push-action/releases` etc.). Se houver major mais nova quando você implementar, use a mais nova e leia o "breaking changes".

## Tarefa 4.5: Release do `shortener-api` (imagem no GHCR a cada merge)

**Arquivos:** criar `.github/workflows/release.yml` no `shortener-api`.

**Conceitos:**
- **Tag imutável por commit** (`sha-abc1234`). Nunca `latest` em deploy.
- **"Build once, deploy many":** a mesma imagem passa por staging e por produção.
- **`APP_VERSION` embutida na imagem.** O `/healthz` mostra qual versão está no ar.
- **Nome da imagem a partir do repo:** `${GITHUB_REPOSITORY,,}` é `<org>/shortener-api` em minúsculas (o `,,` é do bash). Por isso a imagem já sai como `ghcr.io/<org>/shortener-api`.
- **`paths-ignore`:** um merge que só mexe em documentação não gera imagem nova. Agora só sobram `docs/**` e `**.md`, porque infra e manifests mudaram para o `shortener-deploy`.
- **Ainda sem deploy.** O job que atualiza o overlay de staging no `shortener-deploy` entra na Fase 8, junto com o GitHub App.

- [x] **Passo 1: crie** `.github/workflows/release.yml`

```yaml
name: Release

on:
  push:
    branches: [main]
    paths-ignore: ["docs/**", "**.md"]

permissions:
  contents: read

concurrency:
  group: release
  cancel-in-progress: false

jobs:
  ci:
    uses: ./.github/workflows/ci.yml

  image:
    needs: ci
    runs-on: ubuntu-24.04-arm
    permissions:
      contents: read
      packages: write
    outputs:
      image: ${{ steps.vars.outputs.image }}
      tag: ${{ steps.vars.outputs.tag }}
    steps:
      - uses: actions/checkout@v7
      - id: vars
        run: |
          echo "image=ghcr.io/${GITHUB_REPOSITORY,,}" >> "$GITHUB_OUTPUT"   # ,, = minúsculas
          echo "tag=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
      - uses: docker/setup-buildx-action@v4
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          platforms: linux/arm64
          tags: ${{ steps.vars.outputs.image }}:${{ steps.vars.outputs.tag }}
          build-args: APP_VERSION=${{ steps.vars.outputs.tag }}
          labels: org.opencontainers.image.source=https://github.com/${{ github.repository }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

O label `org.opencontainers.image.source` liga o pacote do GHCR ao repositório: ele aparece na página do repo e herda o acesso do repo.

Os outputs `image` e `tag` ainda não são usados. O job de deploy da Fase 8 vai lê-los.

- [x] **Passo 2: faça o commit pela rotina de PR** (branch → PR → CI verde → merge) e acompanhe o Release com `gh run watch`.

- [x] **Passo 3: deixe o pacote público.** No GitHub: página da org (`https://github.com/<org>`) → **Packages** → `shortener-api` → **Package settings** → **Change visibility** → **Public**. Na mesma tela, em "Manage Actions access", confirme que o repositório `shortener-api` tem acesso de escrita.

- [x] **Passo 4: teste a imagem publicada localmente**

```bash
docker logout ghcr.io 2>/dev/null   # garante que o pull é anônimo
docker pull ghcr.io/<org>/shortener-api:sha-<7>
docker run --rm ghcr.io/<org>/shortener-api:sha-<7> node -e "console.log(process.env.APP_VERSION)"   # sha-<7>
```

O `docker manifest inspect` da imagem mostra duas entradas: `linux/arm64` e uma `unknown/unknown`. A segunda não é outra plataforma: é a atestação de *provenance* (como e de onde a imagem foi construída) que o Buildx anexa por padrão.

**Pronto quando:** a imagem `sha-<7>` aparece no GHCR, é pública e o `pull` funciona sem login.

## Tarefa 4.6: CI e Release do `shortener-web`

**Arquivos:** criar `.github/workflows/ci.yml` e `.github/workflows/release.yml` no `shortener-web`.

**Conceitos:**
- Os jobs têm os mesmos nomes da api (`app` e `docker`), então as regras de proteção da Tarefa 4.7 são idênticas nos dois repos.
- **Typecheck:** o template `react-ts` usa project references (`tsconfig.app.json` e `tsconfig.node.json`), então o typecheck é `tsc -b`. O script `build` do template (`tsc -b && vite build`) faz as duas coisas; aqui elas viram passos separados para o log mostrar qual falhou.
- **O e2e (Playwright) não roda no CI.** Ele precisa da api inteira de pé: Postgres, Valkey, Kafka, worker e o IdP mock. Subir tudo isso no CI do web é lento e acopla os dois repos (qual versão da api usar?). Os testes de unidade e de componente (Vitest + MSW) já cobrem o painel isolado. O e2e continua local, e o equivalente na AWS é o smoke pós-deploy (análise `web-smoke` do blue-green na Fase 7 e o teste pelo navegador em staging). Rodar o e2e no CI contra uma api em container fica como extensão.
- **Sem `APP_VERSION` no web.** A imagem do web é só nginx servindo arquivos estáticos; a versão no ar se descobre pela tag da imagem no Rollout. Isso evita mexer no `Dockerfile` e no `nginx.conf` da Fase 3.

- [x] **Passo 1: crie** `.github/workflows/ci.yml` (no `shortener-web`)

## Tarefa 4.7: proteção da `main` (rulesets) na api e no web

**Conceitos:**
- **Rulesets** são a forma atual de proteger branches no GitHub (substituem as "branch protection rules" clássicas e aceitam vários conjuntos de regras por repo).
- Regras desta tarefa, na branch padrão:
  - não pode ser apagada nem receber force push;
  - toda mudança entra por PR (0 aprovações, porque você trabalha sozinho; em time seria 1 ou mais);
  - os checks `app` e `docker` precisam estar verdes, com a branch atualizada em relação à `main`;
  - merge só por squash, para manter um commit por PR.
- Os checks são identificados pelo nome do job (`app`, `docker`). Quando o CI roda via `workflow_call` dentro do Release, o nome vira `ci / app`, mas isso acontece só no push da `main`, que não passa pelo ruleset.
- **O `shortener-deploy` ganha o ruleset dele na Fase 8.** Lá, o job de deploy da api e do web faz commit direto na `main` do deploy, então o ruleset precisa de *bypass* para o GitHub App, que só existe na Fase 8.

- [x] **Passo 1: crie o ruleset nos dois repos**

```bash
for repo in shortener-api shortener-web; do
  gh api "repos/<org>/$repo/rulesets" --method POST --input - <<'EOF'
{
  "name": "main",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] }
  },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    {
      "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 0,
        "dismiss_stale_reviews_on_push": false,
        "require_code_owner_review": false,
        "require_last_push_approval": false,
        "required_review_thread_resolution": false,
        "allowed_merge_methods": ["squash"]
      }
    },
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": true,
        "do_not_enforce_on_create": false,
        "required_status_checks": [
          { "context": "app" },
          { "context": "docker" }
        ]
      }
    }
  ]
}
EOF
done
```

A fonte da verdade do formato é a documentação da API ("REST API endpoints for rules" → "Create a repository ruleset"). No `pull_request`, os 5 campos booleanos/numéricos são obrigatórios, mesmo com o valor padrão.

Pela interface, o caminho é: repo → **Settings** → **Rules** → **Rulesets** → **New branch ruleset**, com target "Default branch" e as mesmas regras.

- [x] **Passo 2 (opcional): ajuste as opções de merge do repo** para combinar com o ruleset

```bash

  gh repo edit "<org>/$repo" --enable-squash-merge --enable-merge-commit=false \
    --enable-rebase-merge=false --delete-branch-on-merge
done
```
